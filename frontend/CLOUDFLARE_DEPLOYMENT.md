# Cloudflare Workers deployment

This frontend uses OpenNext to build the Next.js application for Cloudflare Workers.
Keep the standard `build` script as `next build` for the existing Vercel workflow.

Configure Cloudflare Workers Builds with separate production and preview commands:

- Root directory: `frontend`
- Build command (Production and Previews Base): `npm run cf:build`
- Production Deploy command: `npm run cf:deploy`
- Preview command (Previews Base): `npm run cf:preview`

The Cloudflare-specific scripts in `package.json` are intentionally self-contained:

- `cf:build` runs `opennextjs-cloudflare build`.
- `cf:preview` runs `opennextjs-cloudflare build` again and then `wrangler preview`.
- `cf:deploy` runs `opennextjs-cloudflare build` and then `opennextjs-cloudflare deploy`.

Running the OpenNext build inside the Preview command is deliberate defensive behavior.
Cloudflare's legacy Preview build path may execute the Production build command instead
of the Preview Base build command. In that case, a plain `npm run build` runs only
Next.js and does not create `.open-next/worker.js`. The self-contained `cf:preview`
command regenerates the Worker entry point immediately before starting Wrangler Preview.

Do not put `npx wrangler preview` alone in the Preview command, because it assumes
that the OpenNext Worker bundle was generated by the preceding build command.
Do not put `npx wrangler preview` in the Production Deploy command.

Keep the existing Vercel build command (`npm run build`) unchanged in the Vercel
configuration. The Wrangler configuration is maintained in `wrangler.jsonc`, and
the OpenNext configuration is maintained in `open-next.config.ts`.

Do not promote a preview build to production until its preview URL has been checked
for frontend loading and API/WebSocket connectivity. Keep the existing Vercel
deployment available as a fallback.

## Existing Workers Builds projects: one-time Preview migration

If this Worker was connected to Workers Builds before Worker Previews were introduced,
enabling Preview Builds and filling in the Preview tab is not sufficient. Cloudflare
may retain the legacy Preview model until the one-time migration is completed.

In the Cloudflare dashboard, open the Worker and go to **Settings → Builds**. If the
**Set up Worker Previews** banner is present, choose **Set up**, review the Preview
command, and complete **Switch to Worker Previews**. This is a one-time,
non-reversible switch from the legacy Preview model. Do not change the Production
build or deploy commands as part of this migration.

Also confirm that Preview Builds are enabled and that at least one Preview host is
enabled under the Worker's **Domains** settings (for example, the `workers.dev`
Preview URL). Without a Preview host, the build can succeed but no Preview URL
will be available.

For this repository, a successful Preview build log must show:

1. An OpenNext build that creates `.open-next/worker.js` (either `npm run cf:build`
   or the self-contained `npm run cf:preview`).
2. `wrangler preview` starting without an entry-point error.
3. A Preview URL for the current PR commit.

A build that only runs `npm run build` / `next build`, or a manually deployed
Production build, does not verify the Cloudflare Preview path. Do not merge until
the current PR Preview URL has been checked for frontend loading and backend REST
API/WebSocket connectivity.
